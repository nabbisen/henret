# Migration: v0.18.x → v0.19.0 — resource lifetime & finalization ledger (RFC 057)

**Grammar change.** Additive across four types plus the state:

- a new module `Henret/Resource/Ledger.lean` introducing `ResourceId := Nat`,
  `ResourceState` (`allocated` / `closing` / `released`), `ResourceRecord`
  (`{ owner : TaskId, state : ResourceState }`), and the `markClosingIf`
  bulk-update helper;
- `RuntimeState` gained two fields, `resources : ResourceId → Option
  ResourceRecord` (init `fun _ => none`) and `nextResourceId : Nat` (init `0`);
- `RuntimeOp` gained three constructors — `acquire`, `release`, `finalize`
  (now **24** constructors), ordered immediately after `stopWhenIdle`;
- `StepResult` gained one constructor, `.acquired (r : ResourceId)` (now **10**
  constructors), ordered immediately before `.invalid`.

The `WellFormed` invariant gained **four** fields — fields **30–33**:
`resource_fresh`, `resource_owner_spawned`, `allocated_owner_nonterminal`,
`closing_owner_terminal`. All four are **vacuous on a program that never calls
`acquire`** (the ledger stays empty), so the 29-field base contract is
preserved for any v0.18 program.

## The lifecycle

A resource is **task-owned**: every `ResourceRecord` carries the `TaskId` that
acquired it. There are exactly two paths from acquisition to reclamation, and
the ledger only ever moves a record *forward* along them:

```
                 release t r           (synchronous, by the owner)
  allocated ───────────────────────────────────────────────▶ released
      │                                                          ▲
      │ complete / cancel / fail / cancelTree (owner goes terminal)
      ▼                                                          │
   closing ───────────────────────────────────────────────────┘
                 finalize r            (asynchronous, by the environment)
```

- **`acquire t`** — a *running* task `t` (i.e. `running = some t` and
  `taskState t = some .running`) allocates a fresh resource at the current
  `nextResourceId`, owned by `t` and `allocated`; the counter advances by one
  and the result is `.acquired` of the **old** id. A non-running task's
  `acquire` is `.invalid` (no state change).
- **`release t r`** — the **owning** running task synchronously releases its
  own `allocated` resource: the record flips to `released`. A release by a
  non-owner, or of a resource that is not `allocated` (already `closing` or
  `released`), is `.invalid`.
- **`finalize r`** — the environment reclaims a `closing` resource, flipping it
  to `released`. **There is no running-task guard**: a closing resource's owner
  is by construction terminal, so no task is in a position to finalize it; the
  operation models an out-of-band finalizer. `finalize` of a non-`closing`
  resource is `.invalid`.

**Why terminal transitions close owned resources.** When a task goes terminal
via `complete`, `cancel`, `fail`, or a `cancelTree` that reaches it, every
`allocated` resource it owns is automatically moved to `closing` (by
`markClosingIf`). This is what keeps the two invariants
`allocated_owner_nonterminal` and `closing_owner_terminal` jointly true: a live
task never owns a `closing` resource, and a terminal task never owns an
`allocated` one. The headline coupling theorems are
`complete_marks_owned_resource_closing`,
`cancel_marks_owned_resource_closing`, `fail_marks_owned_resource_closing`, and
`cancelTree_marks_descendant_resource_closing`.

## What is *proved*

The mathematical core is kernel-checked with **zero `sorry` and zero project
axioms**:

- `preserves_wf_acquire` / `preserves_wf_release` / `preserves_wf_finalize`
  carry all **33** `WellFormed` fields across the three operations, and
  `reachable_wf` lifts this to every reachable state.
- The four `reachable_resource_*` projections expose the resource invariants
  directly on reachable states.
- `nextResourceId_monotone_step` / `_run`: the allocation counter never
  decreases, so ids are never reused along a run.
- The per-branch behavioural theorems in `Henret/Proofs/ResourceBranch.lean`
  pin the exact `StepResult` and ledger record of every acquire/release/
  finalize branch.

## What is *trusted*

The **native finalizer is a trust boundary**, not a proved component. Tier 1
models the *ledger* — the bookkeeping of which resource is in which state and
who owns it — and proves the state machine well-formed. It does **not** model
the FFI that performs the actual reclamation (closing a file descriptor,
freeing a buffer). `finalize` is the typed seam a future native-finalizer layer
reasons against; that the OS-level resource is truly released when the ledger
says `released` is an assumption discharged at the bridge, exactly as the
Chase–Lev / epoll bindings are.

## What is *tested*

Ten executable conformance scenarios in `Henret/Conformance/Branch.lean`
(`resource_*`) exercise every reachable branch end-to-end and are kernel-checked
by `branch_suite_passes`; `coverage_complete` ties each to a registry branch.

## What is *not* in scope (Tier 1)

- **No liveness or timeliness guarantee.** Tier 1 proves nothing about *when*
  a `closing` resource is finalized, or that it ever is. A `closing` resource
  may remain closing forever; `finalize` is permitted, not scheduled.
- **`stopped` ≠ resource-drained.** `stopWhenIdle` / `shutdown` stop the
  scheduler when no *task* is runnable. They make **no** claim that the ledger
  is empty: resources may still be `allocated` or `closing` at shutdown. A
  drain-before-stop discipline is deliberately deferred.
- **Resources are task-owned only.** Actor-owned (longer-lived) resources are a
  future tier; in Tier 1 a resource's owner is always the acquiring task.
- **Restart uses fresh ids (Option 1).** A `restartOne` that replaces a failed
  task does **not** inherit or transfer the old task's resources. The old
  (terminal) owner's resources remain `closing` and are reclaimed by
  `finalize`; the replacement starts with no resources and acquires fresh ids.

## Impact on downstream code

You need to act only if your code:

1. exhaustively matches over `RuntimeOp` (add `acquire` / `release` /
   `finalize` arms) or `StepResult` (add an `.acquired` arm), or
2. constructs a `RuntimeState` literally (set the two new fields — `resources
   := fun _ => none` and `nextResourceId := 0` reproduce the empty ledger), or
3. wants to track resources (use `acquire` / `release` / `finalize` and consult
   `RuntimeState.resources`).

Code that consumes the public theorems or uses `run` / `step` / `runTrace`
opaquely, and never calls `acquire`, is behaviourally unaffected: the ledger
stays empty and the four new invariants are vacuous.
