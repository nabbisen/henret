# Migration: v0.17.x → v0.18.0 — bounded mailboxes & backpressure (RFC 056)

**Grammar change.** Additive across three types:

- a new record `MailboxPolicy` (`{ capacity : Option Nat }`) with
  `MailboxPolicy.unbounded := { capacity := none }`;
- `RuntimeState` gained one field, `mailboxPolicy : ActorId → MailboxPolicy`,
  initialised to `fun _ => .unbounded`;
- `StepResult` gained one constructor, `.backpressured` (now **9**
  constructors), ordered immediately before `.invalid`.

`RuntimeOp` is **unchanged** (still 21 constructors): backpressure is a new
*result* of the existing `send`/`inject`, not a new operation.

The `WellFormed` invariant gained one field — field **29**,
`mailbox_within_capacity` — stating that no mailbox's length ever exceeds its
configured capacity. The field is **vacuous under the default unbounded
policy** (`capacity = none`), so the 28-field base contract is preserved for
any program that never configures a bound.

## What changed

RFC 056 implements **Option A (reject-only)** backpressure:

- `send t b m` and `inject a m` now consult `mailboxPolicy b` / `mailboxPolicy a`.
  When the target mailbox is at capacity the delivery is **rejected** and the
  step returns `.backpressured` — a **no-op result**: the state is unchanged,
  no message is enqueued, and (per the occurrence-id discipline) **no
  occurrence id is consumed** (`nextMsgId` does not advance on a backpressured
  attempt). This is proved by `step_backpressured_unchanged`.
- The capacity guard is placed **after** all validity guards (closed-actor,
  running, owner, mailbox-exists). A send that would otherwise be `.invalid`
  stays `.invalid`; only an otherwise-valid delivery can be backpressured.
  `.backpressured ≠ .invalid` (`backpressured_not_invalid`).
- **Capacity zero is a documented reject-all policy**: a mailbox with
  `capacity = some 0` rejects every delivery and never holds a message.
- **A Mesa waiter does not imply an empty mailbox.** Delivery wakes the head
  waiter, but the message remains queued until that task is scheduled and
  actually receives. A second waiter therefore coexists with a full mailbox,
  and a further delivery is backpressured even though a waiter is present
  (conformance scenarios `full_mailbox_with_waiter_{send,inject}_backpressured`).

**The default is unbounded.** Under `mailboxPolicy = fun _ => .unbounded`
`mailboxFull` is always `false`, so `send`/`inject` are **never**
backpressured (`send_unbounded_not_backpressured`,
`inject_unbounded_not_backpressured`). Any v0.17 program is byte-for-byte
behaviourally identical on v0.18 until it sets a bound.

**Bridge.** The single-worker bridge stays queue-stable: `toQOps` now emits
`[]` for a delivery to a full mailbox (matching the backpressured no-op), so
`bridge_send` / `bridge_inject` continue to hold.

## What is *not* in scope

**Option B (park-policy / blocking senders)** — where an over-capacity send
parks the sender rather than rejecting — is explicitly **not implemented**.
A future Option-B RFC may introduce a blocking result (`.sendBlocked` or a
`.parkedSend`); `.backpressured` remains the reject-policy result. RFC 056 also
makes no liveness, fairness, or drain-progress claim.

## Impact on downstream code

You need to act only if your code:

1. exhaustively matches over `StepResult` (add a `.backpressured` arm), or
2. constructs a `RuntimeState` literally (set the new `mailboxPolicy` field —
   `fun _ => .unbounded` reproduces the prior behaviour), or
3. wants bounded mailboxes (set `mailboxPolicy a := { capacity := some n }`
   for the actors you want to bound) and must handle `.backpressured` from
   `send`/`inject`.

Code that consumes the public theorems or uses `run`/`step`/`runTrace`
opaquely, and leaves every mailbox unbounded, is unaffected.
