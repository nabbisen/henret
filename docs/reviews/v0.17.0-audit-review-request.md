# v0.17.0 Audit — Architect Review Request

**Prepared after:** the post-v0.17.0 (RFC 055) five-dimension audit
(does the codebase fulfil the done RFCs; dead code; tests vs requirements;
codebase vs tests; docs vs codebase).

**Purpose.** The audit surfaced a set of **judgment-call items** — issues
where the correct action is a design/process decision, not a mechanical
fix. Each is written up below so it can be reviewed and decided **one at a
time**. None blocks the v0.17.0 release; all are about long-term health.

**Already fixed during the audit (not for review — listed for context):**
the audit-gate heredoc/allowlist drift (a stale `run_preserves_owner`,
~26 unsynced allowlist entries), two examples broken since RFCs 031/033
(`07` Envelope arity, `08` missing `WellFormed` arg), and two stale
current-tense "12 operations" doc/docstring claims
(`docs/bridge-architecture.md`, `Henret/Bridge/Grammar.lean`). The full
library builds with zero `sorry` / zero project axioms, the axiom audit
exits clean, conformance is 10/10, and all examples + the Explore harness
pass.

## A1 — Dead helper lemmas in `StepFields.lean`

**Category:** dead code. **Severity:** low–medium.

**Finding.** `Henret/Proofs/StepFields.lean` (shipped by RFC 042 to bundle
the most repetitive `WellFormed` preservation bullets) exports a family of
`wf_*_pass` helper lemmas. Eight of them are referenced **zero** times
anywhere outside the file:

- `wf_parent_spawned_pass`
- `wf_occ_pass` (the bundled occurrence helper)
- `wf_timed_has_deadline_pass`
- `wf_deadline_is_timed_pass`
- `wf_timed_has_timer_pass`
- `wf_timed_is_waiter_pass`
- `wf_timed_waiters_valid_pass`
- `wf_timed_waiters_nodup_pass`

For contrast, four siblings *are* used (`wf_occ_fresh_pass`,
`wf_occ_nodup_pass`, `wf_occ_disjoint_pass` 8× each; `wf_parent_lt_pass`
9×). So the helper pattern works and is adopted for the occurrence and
`parent_lt` fields, but the **timed-waiter family (RFC 040 fields) and a
few others were never wired into the preservation proofs** — including the
proofs I just edited for RFC 055, which hand-write those bullets instead.

**Why it's a judgment call.** These are not "planned/future" helpers for
unbuilt features — they target fields that already exist. They are either
(a) latent infrastructure worth keeping and adopting, or (b) genuinely
dead and worth removing. The right answer depends on whether the team
intends to standardise preservation proofs on these helpers (see A2).

**Options.**
- **A — Adopt.** Refactor the timed-waiter / parent-spawned bullets in
  `Preservation/{Lifecycle,Messaging,Time}.lean`, `Restart.lean`, and
  `Shutdown.lean` to call the helpers. Realises RFC 042's intent and
  shrinks the proofs.
- **B — Delete.** Remove the eight unused lemmas; keep only the four that
  are used. Smallest, simplest, but concedes RFC 042's goal.
- **C — Defer.** Leave as-is, accept the dead weight until a proof-ergonomics
  RFC revisits it.

**Recommendation:** **A**, bundled with A2 — adoption is the only option
that both removes the "dead" status *and* advances the original goal.
Deleting (B) is the cheap correct fallback if no proof-ergonomics work is
planned.

**Decision:** ☐ Adopt (A) ☐ Delete (B) ☐ Defer (C)

## A2 — RFC 042's stated goal is unrealized

**Category:** done-RFC fulfilment. **Severity:** medium.

**Finding.** RFC 042 ("Preservation Proof Automation", Implemented
v0.10.1) set out to "reduce repetitive `WellFormed` preservation code as
the invariant grows" and to "prevent proof drift." Its deliverable
(`StepFields.lean` helper lemmas) exists, but the **outcome was not
achieved**: the per-operation preservation proofs remain large and
copy-paste-heavy. RFC 055 is direct evidence — closing one semantic-core
extension required hand-threading admission guards through hundreds of
lines of per-field bullets across ~6 proof files, with the exact
copy/paste drift RFC 042 was meant to prevent. A2 is the *why* behind A1.

**Why it's a judgment call.** RFC 042 is marked Implemented and did ship
*a* deliverable, so this is not a "lied about done" case. The question is
whether the gap is acceptable (the proofs are verbose but correct and
auditable) or whether it warrants reopening the automation effort — and if
so, whether to amend RFC 042's status, supersede it, or file a fresh RFC.

**Options.**
- **A — Accept.** Treat verbosity as a deliberate auditability trade-off;
  annotate RFC 042 to say the lemma helpers are the intended ceiling and
  metaprogramming was explicitly declined.
- **B — Follow-up RFC.** File a new proof-ergonomics RFC that (i) adopts
  the existing helpers (A1-A), (ii) adds per-operation-family
  "unchanged-fields" lemmas so a guard-wrap is one line, and (iii) measures
  the before/after line count. Mark RFC 042 *Superseded by* it.
- **C — Amend 042.** Reopen under the same number with a v2 deliverable
  (discouraged by RFC 000 — superseding is cleaner than reopening).

**Recommendation:** **B.** The cost is real and recurring (every future
core extension pays it), and a measurable, lemma-based (not macro-based)
follow-up is low-risk. This is the single most leverage-positive
engineering item in the audit.

**Decision:** ☐ Accept (A) ☐ Follow-up RFC (B) ☐ Amend 042 (C)

## A3 — Conformance suite under-covers the grammar

**Category:** tests vs requirements / external design. **Severity:** medium.

**Finding.** The golden conformance suite (`Henret/Conformance/Golden.lean`,
RFC 047 — the project's *external-design regression artifact*) has **10
scenarios, all covering features at or before RFC 033**:
`spawn_schedule_complete`, `yield_requeues`, `sleep_tick_wakes`,
`empty_receive_parks`, `send_wakes_waiter_mesa`, `inject_wakes_waiter_mesa`,
`cancel_ready_task`, `cancel_waiting_task`, `spawn_child_parent_lt`,
`occurrence_unique_two_mailboxes`.

No golden scenario exists for any operation added since:
`receiveUntil` (RFC 040), `receiveByOccurrence` / `receiveFrom` (041),
`fail` / `restartOne` (049), or `closeActor` / `shutdown` / `stopWhenIdle`
(055). Those are exercised only by `examples/`, which are
compile-and-`#eval` checks — weaker than golden traces with asserted
results, and not part of the regression artifact external consumers would
run.

**Why it's a judgment call.** The suite is not *wrong* — every scenario in
it passes and matches the model. The question is the **intended role** of
the golden suite: if it is the canonical conformance contract (RFC 047's
framing), it should track the grammar; if it is a fixed smoke-test, the
current 10 may be sufficient and example coverage is the safety net.

**Options.**
- **A — Extend the suite** with golden scenarios for the ~7 uncovered
  operations (timed receive timeout & wake, selective receive hit/miss,
  fail→restart provenance, closeActor-rejects-send, shutdown-rejects-spawn,
  stopWhenIdle-from-quiescent). Small, mechanical, raises the regression
  floor.
- **B — Define the suite's scope** explicitly as a curated smoke test and
  document that per-feature coverage lives in `examples/` — then add a gate
  asserting every `RuntimeOp` constructor appears in *either* the suite or
  a named example.
- **C — Defer.**

**Recommendation:** **A**, with the **B** gate as a durable guard so the
suite can't silently drift behind the grammar again.

**Decision:** ☐ Extend (A) ☐ Scope + coverage gate (B) ☐ Defer (C)

## A4 — RFC status-field format is inconsistent

**Category:** docs/process. **Severity:** low.

**Finding.** Across the 55 done RFCs, three status-field styles coexist:

| Style | Count | Example |
|-------|-------|---------|
| YAML-ish `status:` | 34 | `status: Implemented (v0.1.0)` |
| `**Status.**` (the shape RFC 000 *shows*) | 10 | `**Status.** Implemented (v0.12.1)` |
| `## Status` header | 11 | `## Status\n\nImplemented (v0.17.0).` |

All 55 carry *a* valid status, so index integrity holds. Note RFC 000
explicitly says the format "is up to each project" and only *shows*
`**Status.**` as "one common shape" — it does not mandate it. So this is
genuine convention drift, not a policy violation, and the most common
actual form (YAML, 34×) is **not** the one RFC 000 illustrates.

**Why it's a judgment call.** Purely cosmetic; the only concrete cost is
that tooling (e.g., a future status linter, or the audit's own status
check) must handle three formats. The decision is which form to bless.

**Options.**
- **A — Normalize to `## Status`** (the newest convention, easiest for
  humans and `grep`), migrate the other 45, and update RFC 000's example.
- **B — Normalize to YAML `status:`** (current majority; machine-friendly;
  pairs well with A6 doc-extraction).
- **C — Accept the mix**, but add the format to RFC 000 as "any of these
  three" so it's documented rather than accidental.

**Recommendation:** **B** if A6 (doc-extraction) is pursued (YAML front
matter is the natural source for a generated index); otherwise **A** for
human readability. Either way, do it as a single mechanical migration
commit per RFC 000's guidance, and update RFC 000's example to match.

**Decision:** ☐ `## Status` (A) ☐ YAML (B) ☐ Document the mix (C)

## A5 — `lean-runtime-workspace` is absent from this checkout

**Category:** scope/packaging. **Severity:** medium (clarity).

**Finding.** The architecture documents and handoffs describe a second
package, `lean-runtime-workspace/lean-runtime/` — the concrete C Chase-Lev
runtime plus the `runtimeTests` differential / linearizability / stress
harnesses that back the "tested" tier of the proof/trust/test matrix. That
package is **not present** in the current checkout (only the formal-model
package is here), and the v0.17.0 release tarball is the model package
only.

**Consequences for the audit:** RFC deliverables and matrix "TESTED" rows
that live in that package (much of RFC 010's FFI, the concurrent harnesses)
**could not be verified** from this checkout. The in-model
`Henret/Native/` FFI-spec layer (the 6 typed axioms + abstract deque
model) *is* present and proven.

**Why it's a judgment call.** This is a deliberate-architecture vs
accidental-omission question only the maintainer can answer.

**Options.**
- **A — Intended split.** The runtime is a separately-versioned sibling
  repo/package. Then: document the boundary in the README and the matrix
  (mark which "TESTED" rows live out-of-tree), and ensure *that* package
  has its own gate run — otherwise the "tested" tier is unverified at
  release time.
- **B — Should be in-tree.** Restore it as a workspace member so a single
  `lake build` + test run covers both tiers; the release tarball then
  carries both.
- **C — Deprecated.** The runtime experiment is shelved; update the
  matrix/handoffs to stop claiming the concurrent harnesses as live
  evidence.

**Recommendation:** Confirm which of A/B/C is reality, then make the
**honesty ledger match**: the proof/trust/test matrix currently asserts
TESTED rows whose evidence isn't in this tree, which is exactly the kind of
claim the project's honesty discipline exists to prevent.

**Decision:** ☐ Intended split — document boundary (A) ☐ Restore in-tree (B) ☐ Deprecate + correct ledger (C)

## A6 — Doc-count discipline is manual and the stale-phrase gate is leaky

**Category:** docs vs codebase. **Severity:** medium.

**Finding.** Documentation repeats facts that live in the source —
operation counts, `WellFormed` field counts, constructor counts, the
theorem→file index — and they drift. This audit (and the prior session)
found and fixed: "twelve/18/21 operations", "19-field", a non-existent
`run_preserves_owner` in the audit gate, and a stale-phrase gate that
banned `"12-operation"` (hyphen) but not the prose `"12 operations"`,
letting two current-tense stale claims through. The drift is recurrent
because the gate is a hand-maintained `grep` blocklist that grows reactively.

**Why it's a judgment call.** The reactive gate *works* once a phrase is
registered, but it can only ban phrases someone thought to add. The
alternative — generating doc tables from the Lean source (the existing
**proposed RFC 075**, "Model-to-Documentation Extraction") — removes the
drift class at the root but is real work.

**Options.**
- **A — Pursue RFC 075.** Generate the operation/field/constructor tables
  and the theorem index from a single checked metadata source (or directly
  from declarations). Highest leverage; eliminates the class.
- **B — Strengthen the gate only.** Add a positive check: assert the
  *current* counts in docs match the Lean reality (e.g., a script that
  computes `RuntimeOp` constructor count and greps for any disagreeing
  "N operations" claim). Cheaper than 075, catches counts but not prose.
- **C — Status quo.** Keep extending the blocklist reactively.

**Recommendation:** **A** (promote RFC 075) as the strategic fix, with
**B** as an immediate stopgap. This is the same root cause as the gate
issues fixed last session — worth closing properly.

**Decision:** ☐ Promote RFC 075 (A) ☐ Positive count-check gate (B) ☐ Status quo (C)

## A7 — Release gates have not been running end-to-end

**Category:** process integrity. **Severity:** HIGH (highest in this list).

**Finding.** The audit established that `scripts/check.sh` could not have
been passing cleanly end-to-end before this session: gate 7 (axiom audit)
referenced a non-existent theorem and had ~26 allowlist entries unsynced
with the heredoc; gate 5 (examples) had two examples broken since RFCs
031/033. Both are now fixed, but the fact that they *accumulated* means
the gate suite was being run partially or not at all (consistent with the
documented OOM on gates 1/4 in the sandbox, and a habit of validating via
a subset). The codebase itself is sound — this is purely a
**verification-process** gap, which is arguably more dangerous than a code
bug because it lets other regressions hide.

**Why it's a judgment call.** The fix is partly environmental (the demo
build OOMs in-sandbox) and partly procedural (no enforced full run). The
maintainer must decide how the gate is *guaranteed* to run.

**Options.**
- **A — CI enforcement.** Wire `scripts/check.sh` into the `.github`
  workflow on a runner with enough memory to build the demo, so every
  gate runs on every change and drift fails the build. (Verify whether the
  existing `ci.yml` already attempts this and why it isn't catching drift.)
- **B — Split the demo out of the default build** so the full gate suite
  runs in constrained environments without OOM (e.g., make `henret-demo`
  a separate, optional target), and make `check.sh` self-test its own
  heredoc/allowlist consistency.
- **C — Manual discipline.** Document a release checklist requiring a full
  `check.sh` run on an adequate machine before any tarball.

**Recommendation:** **A + B together.** B removes the in-sandbox blocker;
A makes "all nine gates green" a non-negotiable, machine-enforced gate
rather than a hand-run ritual. Until one of these lands, treat any "gates
pass" claim as needing an explicit full-run confirmation.

**Decision:** ☐ CI enforcement (A) ☐ Demo-split + self-test (B) ☐ Checklist (C) ☐ A+B

## A8 — Unused-variable linter warnings

**Category:** cleanliness. **Severity:** trivial.

**Finding.** The full build emits five `unused variable` warnings (errors
are not raised; correctness is unaffected):

- `Henret/Scheduler/Model.lean:133` — `hp`
- `Henret/Proofs/StepProjections.lean:126` — `hfresh`
- `Henret/Proofs/Messaging.lean:365–367` — `hrt`, `hts`, `how`
  (over-specified hypotheses on a theorem that doesn't use them)

**Why it's a judgment call.** Two cheap resolutions with slightly
different meaning: rename to `_`-prefixed (silences), or — for the
Messaging case — actually drop the unneeded hypotheses (tightens the
theorem's statement). The latter is a small API change.

**Options.**
- **A — Underscore the bindings** (silence, zero API change).
- **B — Drop the unused hypotheses** where they're genuinely unneeded
  (Messaging:365–367), underscore the rest. Tightens the public lemmas.
- **C — Suppress** with `set_option linter.unusedVariables false` (least
  preferred — hides future real warnings).

**Recommendation:** **B.** Underscore the proof-local ones; drop the three
unused hypotheses from the Messaging lemma so its statement is honest.
Avoid C.

**Decision:** ☐ Underscore (A) ☐ Drop + underscore (B) ☐ Suppress (C)

3. **A2 → A1** (proof ergonomics, then the dead helpers that depend on it).
4. **A3** (conformance coverage) and **A6** (doc extraction) — both
